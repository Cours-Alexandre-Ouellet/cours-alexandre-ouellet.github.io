    Documentation technique

    La documentation technique est celle qui accompagne un système est qui est destinée au personnel technique (et non aux personnes utilisatrices lambdas). Elle est donc rédigée dans un vocabulaire technique et explique le fonctionnement du code plutôt que le fonctionnement du système. Les commentaires servent à comprendre l'utilité d'un bout de code sans avoir à en lire le code. Elle peut aussi servir lors de la mise à jour d'un système pour se rappeler les décisions de design faites, ainsi que les emprunts de code externes.

    Pourquoi documenter les emprunts de code

    Les outils changent, les réponses sur les forums aussi. Un code pris d'un forum (ou pire, de ChatGPT) peut être critiqué ou révoqué après la publication, car il ne s'agit pas d'une bonne pratique. Il ne faut pas faire confiance à tout ce qui provient d'internet.

    Également, sans être révoquées, certaines nouvelles solutions sont publiées sous une vieille réponse de forum, ou des liens sont proposés vers les mêmes questions, mais plus récentes. Repartir de la source de l'emprunt aide la mise à jour du code.

    Rédiger une bonne documentation technique - la recherche

    Dans une revue de systématique de littérature publiée en 2023, Rani et coll. ont revu 2353 publications sur les commentaires dans le code qui ont eu lieu entre 2011-2020 et en ont sélectionné les publications 47 les plus pertinentes. Ces dernières se sont intéressées aux critères des bons commentaires de code : elles en ont trouvé 21. Voici des critères de qualité qui reviennent le plus souvent dans la littérature.

    Consistance
    Les termes du code source sont ceux utilisés dans les commentaires. Par exemple, dans un système de gestion d'école, on utilise le terme étudiant ou élève, mais pas les deux et surtout pas de façon interchangeable.
    Complétude
    Tous les types publics sont commentés, et ce, sans exception. De plus, si les méthodes excèdent 30 lignes de code ou réalisent plus de 3 appels à d’autres méthodes, elles ont des commentaires internes pour expliquer leur fonctionnement.
    Précision
    Il n'existe pas de critère pour mesurer la précision. D'expérience, si vous recevez régulièrement des demandes d'information (ex. des courriels de vos collègues) pour expliquer une partie de votre code, il est probablement que sa documentation ne soit pas assez précise.
    Lisibilité
    Les termes non techniques sont du langage courant. On avait précédemment défini le niveau de langage technique comme le langage courant, augmenter des mots du domaine technique. Des tests et des mesures (comme le test de Flesh) permettent de vérifier le niveau de langage d'un texte, principalement en vérifiant l'usage de phrases courtes et de termes usuels.
    Actualité (*up-to-date-ness*)
    Chaque changement dans le code devrait être accompagné des changements correspondant dans la documentation. Il n'existe pas de mesure de cet attribut autre que si vous recevez des questions fréquentes concernant le même bout de code, peut-être n'avez-vous pas mis la documentation à jour. Cela rejoint un autre critère de qualité de la documentation : assurer la maintenabilité.
    Pertinence du contenu
    Il n'existe pas de critère pour mesurer la pertinence, on évite toutefois d'énoncer des évidences. Si l'on doit le faire, on le fait aussi brièvement que faire se peut.
    Orthographe et grammaire
    Comme tout contenu écrit, une partie de l'interprétation correcte par la personne qui relie vos commentaires de l'information que vous vouliez lui transmettre passe par la bonne compréhension des mots. Souvent, les commentaires contiennent des erreurs de sujet ou de prédicat manquant ainsi que de nombreuses erreurs de ponctuation. Ces deux types d'erreurs peuvent changer (parfois drastiquement) l'interprétation d'un commentaire.
    Utilisabilité des commentaires
    Le nombre de mots dans les commentaires de méthodes devrait être relativement bas. Un standard est proposé à 30 mots et moins (comme c'est de l'anglais, on pourrait parler de 40 mots en français). Les commentaires des classes eux peuvent être très longs pour bien expliquer les rôles de ce type de données et les cas d'usage. Si c'est plus court de lire le code que la documentation, alors cette dernière est définitivement peu utile.

    Rédigier une bonne documentation technique - l'expérientiel

    Un utilisateur de StackOverflow a publié 9 règles pour rédiger de bons commentaires de code (Spertus, 2021) dans le blogue de StackOverflow. Voici les 9 règles à suivre :

    1. Les commentaires ne devraient pas dupliquer le code.
    2. De bons commentaires ne sont pas une excuse pour du code peu clair.
    3. Si ce n’est pas possible d’écrire un commentaire clair, il peut y avoir un problème avec le code.
    4. Les commentaires doivent limiter la confusion et non provoquer celle-ci.
    5. Expliquer le code qui n’est pas évident dans les commentaires.
    6. Inclure des liens vers le code copié-collé.
    7. Inclure des références vers des ressources externes lorsque c’est utile.
    8. Ajuster des commentaires lorsqu’on règle des bogues (surtout par hotfix).
    9. Utiliser les commentaires pour les implémentations incomplètes.

    L'expérientiel plus que la recherche ?

    C'est un piège dans lequel il est facile de tomber de privilégier que les règles de l'expérience (souvent exprimées par une seule personne ou, au contraire, des règles du type tout le monde sait bien que...) face à des résultats de recherche qui peuvent sembler distants des pratiques.

    Exercice : essayer de dresser un parallèle entre les deux critères. Vous verrez que les deux expriment des idées similaires, mais dans un vocabulaire différent.

    Javadoc

    En java, un outil appelé javadoc permet de générer facilement une documentation technique de votre code pour référence et partage. Dans gradle, vous trouverez une tâche pour générer la javadoc à partir des commentaires de votre code
