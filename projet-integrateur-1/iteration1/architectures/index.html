Patrons de conception et architecture

Un patron de conception est une solution réutilisable, empiriquement validée, pour répondre à un problème dans la conception d’un logiciel (Design pattern). C’est la conception de l’organisation du système (indépendante des problèmes considérés individuellement) et la structure pour supporter l’organisation choisie.

Les deux se présentent comme des solutions standards à suivre, mais l'une intervient pour résoudre un problème (souvent de gestion du couplage) alors que l'autre sert de ligne directrice dans l'organisation. On ne choisit pas un patron de conception à appliquer, le contexte du développement nous pousse à utiliser un patron, tandis que l'on choisit consciemment et dès le début d'un projet l'architecture à utiliser.

La place de l’architecture dans la conception

Là où la conception des cas d’utilisation en fonctionnalité répond aux besoins du client, la conception de l’architecture répond aux besoins des programmeuses et programmeurs à organiser un système pour être capable de répondre aux besoins du client.

  3. Conception des algorithmes

Si l'on revient au manifeste agile présenté précédemment, le 9e principe va comme suit : « Un souci continu de la qualité technique et de bonne conception augmente l'agilité. » L'architecture est l'une des principales pièces sur laquelle asseoir la capacité d'adaptation du système.

Une bonne architecture logicielle comprend :

  • Des mécanismes flexibles pour ajouter des fonctionnalités (stratégie, décorateur, visiteur, composant, état, commande, fabrique)
  • Des mécanismes pour limiter la propagation des changements dans le système (adaptateur, façade, observateur)
  • Une sémantique d’abstractions pour séparer les types de préoccupations fonctionnelles et non fonctionnelles

En bref, une architecture augmente la flexibilité du système et sa capacité à s’adapter au changement.

Architectures communes

Les architectures suivantes permettent de structurer un système. Elles peuvent s'utiliser individuellement ou en combinaison. Un tableau résume leurs principales caractéristiques, puis une description plus complète suit.

Architecture Description et rôle
MVC Structure le système en trois couches pour séparer les responsabilités liées à l'affichage des données, la structure des données et le contrôle des données.
Localisateur de service Regroupe des fonctionnalités dans des classes de service afin de leur donner un point d'accès unique et réduire les ressources utilisées.
DAO Encapsule la logique pour enregistrer ou charger des données pour éviter de lier la gestion des supports d'enregistrement et la logique métier.
Rest API Sépare la gestion des données et l'affichage en deux systèmes distincts. Le système d'affichage des données ne conserve aucun état quant à l'état des données et est complètement dépendant du système de gestion.

MVC : Modèle-vue-contrôleur

L'architecture MVC (MVC : model-view-controller) divise les classes en 3 catégories. Chaque catégorie est associée à un ensemble de responsabilités distinct et l'architecture dicte la nature et la façon dont l'information circule entre les diverses couches.

  • Modèle : représentation des données dans le système. La couche modèle peut effectuer des traitements sur l'intégrité des données ou sur la logique métier.
  • Vue : affichage et saisie des données. La couche vue définit des interfaces desquelles les données ne dépendant pas.
  • Contrôleur : contient la logique applicative et gère les accès aux données par les vues. Tout ce qui ne relève pas directement de la logique métier se trouve dans cette couche. On peut la voir comme le chef d'orchestre du système.

Il n’y a de changement ou d'indication dans le code source pour utiliser MVC : tout est une question sémantique, de rigueur et de discipline dans l’organisation du code.

À l'appel d'une fonctionnalité dans le système :

  1. La vue appelle le contrôleur associé à la fonctionnalité et lui transmet les données.
  2. Le contrôleur gère la logique applicative (authentification, validation des données ...).
  3. Le contrôleur crée les modèles associés aux données (en chargement de la BD ou en initialisant les objets).
  4. Les modèles appliquent la couche de logique métier sur les données.
  5. Le contrôleur gère l'enregistrement des données (s'il y a lieu).
  6. Le contrôleur génère la vue à partir des résultats des traitements.
  7. La vue s'affiche.

On voit clairement dans cet ordre d'opération un cycle : vue contrôleur modèle contrôleur vue.

Avantages

Limitations

  • Peut s’utiliser dans une variété de systèmes.
  • Permet de séparer les responsabilités.
  • Permet de changer de plateforme (vue) avec peu de réusinage.
  • Facilite les tests unitaires ou d’intégration en séparant les traitements.
  • Limitations de l’effet d’ondes (ripple effect) dû aux modifications.
  • Ajoute un niveau d’abstraction (complexifie l’organisation du code).
  • Augmente le risque de fort couplage (nécessite souvent des patrons comme Médiateur ou Façade).
  • La décomposition en 3 catégories peut entraîner une dispersion ou duplication du code.
  • Peut être complexe à synchroniser avec des applications qui réagissent en temps réel.

Localisateur de services

Il regroupe les instances de plusieurs classes qui agissent en support d’autres classes (comme des utilitaires). Des exemples de classes utilitaires sont des classes qui effectuent des calculs (classes de statistiques), qui journalisent des données (logging), qui manipulent des fichiers de données ou qui permettent la connexion à une base de données...

Le localisateur fournit une interface unique pour accéder à des instances de ces classes sans devoir toujours utiliser le patron Singleton ou de créer inutilement plusieurs copies de l’objet. Lorsque combiné adroitement avec l’architecture MVC, ce patron permet d’éliminer complètement l’utilisation de classes statiques ou du patron Singleton.

Avantages

  • Évite le recours aux constructions statiques qui peuvent être accédées de partout dans le programme (renforce l’utilisation de la programmation-objet).
  • Réduit le coût d’initialisation à répétition des mêmes classes.
  • Permet aussi de gérer les dépendances entre les services et d’encapsuler ces préoccupations dans une partie du système.

Désavantages

  • Peut être complexe à passer entre les vues ou il demande lui-même d’être un Singleton (Un Singleton pour les gouverner tous... ).
  • La réutilisation d’instances peut entraîner des effets de bord
  • La réinitialisation des instances ou la programmation «sans-état» peut impliquer un effort supplémentaire.

Data Access Object (DAO)

Ce patron isole la gestion du stockage des données en mémoire secondaire (système de fichier, base de données) du reste du système. Facilite la représentation des données dans plusieurs formats.

Représente une implémentation des patrons Façade, Adaptateur et Fabrique simultanément pour répondre aux enjeux de stockage des données.

Avantages

  • Interface robuste aux changements de base de données (environnement dev / prod)
  • Isole la manipulation des données à une partie du système

Limitations

  • Surcharge de traitement comme le DAO risque de travailler sur tout l’objet (lenteur)
  • Danger de répétitions de code
  • Peut être difficile de charger des objets de façon optimale (risque d’opérations inutiles)

Les architectures MCV, localisateur de service et DAO sont mis en action dans ce projet : Dépôt du système de voyage

REST API

L'architecture REpresentational State Transfer sépare l'affichage des données et leur manipulation de leur logique de traitement et de stockage en deux applications qui communiquent entre elles par un réseau. On utilise habituellement un protocole comme HTTP pour la transmission des données. L'application cliente est généralement sans état (ne retient aucune information) distribué sur internet, alors que l'information est gérée par un système central de type serveur.

API vs REST

Une Application Public Interface est un système qui permet la communication entre deux systèmes et REST est la spécification de la façon dont la communication se fait. L'utilisation des actions et fonctionnalités exposées relève de l'API alors que la structure des requêtes est le modèle REST.

Avantages

  • Sépare l'évolution du client et du serveur
  • Utilise une interface standard, contrairement à une API définie sur mesure pour un système
  • Facile d'augmenter la taille, car chaque requête est complète, indépendante et sans état

Désavantages

  • Risque d'erreur élevé, car il y absence de typage dans la transmission des données
  • Difficulté avec les requêtes complexes ou imbriquées; une multiplication des requêtes peut survenir
  • Effort de validation et d'authentification augmenté en raison de l'absence d'état de la part du client

Les REST API occupent aujourd'hui une place de choix, mais il reste que ce n'est pas toutes les situations dans lesquelles une REST API devrait être développée. Par exemple :

  • Lorsque les données sont très complexes ou très simples
  • Quand il faut une performance rapide (comme du streaming)
  • Quand les données sont sensibles

Ces situations sont difficiles à gérer avec un REST API en raison des désavantages et de sa structure et du protocole de communication utilisé.
