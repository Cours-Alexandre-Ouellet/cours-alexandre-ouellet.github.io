Temps requis

30 minutes

Description des cas d'utilisation

  • Description abrégée : présente sous la forme d'un paragraphe de texte détaillant uniquement le scénario principal ainsi que les informations d'en-tête. Elle peut être accompagnée ou non d'un prototype d'écran. Ce type de description se prête bien à des cas simples et au début de l'analyse. Un cas peut être décrit sommairement dans l'un des premières itérations avant d'être étendu à une description détaillée dans un cas subséquent.

  • Description détaillée : présente tous les aspects du CU par étapes détaillées. Cette description est plus longue à faire, mais à l'avantage d'être exhaustive et représentative du flux de travail. Si la description d'un cas détaillé n'inclut aucune nouvelle extention ou exception et que son scénario nominal est bref, probablement qu'une description abrégée serait plus approprié.

Parties d'un cas d'utilisation

information d'en-tête
Présente les informations principales du cas d'utilisation dont :
  • Son nom
  • Son code
  • La version dans laquelle il a ét introduit dans les spécifications
  • Le nom de la personne autrice de la description
Préconditions
Les préconditions sont des conditions vérifiées lors de l'exécution du CU. Aucun des éléments présentés dans les préconditions devrait se retrouver dans la description. Il s'agit d'état du système vérifiable.
Postconditions
Pour les postconditions, il s'agit de conditions vérifiées lors de la conclusion avec succès du scénario nominal. Il s'agit d'état du système.
entité actrice principale
L'entité actrice principale est l'entité (ou les entités) actrice qui utilise le CU. Il peut s'agir d'entités primaires ou secondaires.
déclencheur
Le déclencher correspond à une opération qui permet l'accès ou le lancement du CU. On ne répète pas l'opération dans le scénario nominal.
description abrégée (uniquement pour les cas abrégés)
Présente en un ou deux paragraphes le fonctionnement du CU sous forme d'un texte continu. Ce genre de description présente uniquement le scénario de succès et certaines erreurs majeures. Si les erreurs sont nombreuses ou demandent une gestion avancée, on préfère utilier la description longue.
scénario nominal (uniquement pour les cas détaillés)
C'est le scénario de base, souvent le plus simple, et celui qui se termine par un succès. Toutes ses étapes doivent être exécutées. Pour chaque étape, on identifie les actions de l'entité actrice et les réponses du système. La première étape est ce qui suit immédiatement la réalisation du déclencheur. On peut utiliser un tableau ou une liste pour ce faire. Dans tous les cas, on utilise une syntaxe de la forme : [ENTITÉ] + [VERBE D'ACTION] + [ACTION].
scénario d'exception (uniquement pour les cas détaillés)

Ce sont les erreurs qui peuvent survenir ainsi que la façon d'y répondre. Pour chaque erreur, on lui assigne un code basé sur l'étape à laquelle l'erreur peut survenir. Si plusieurs erreurs peuvent se produire à la même étape, on ajoute une lettre minuscule, en ordre alphabétique, pour les différencier. Si l'erreur peut se produire à plusieurs ou toutes les étapes, on utilise le * plutôt qu'un numéro d'étape.

On décrit ensuite de façon détaillée (souvent en liste) les étapes pour ramener le système dans un état cohérent. Si l'erreur interrompt l'exécution du CU, il faut le préciser clairement.

scénario d'extension (uniquement pour les cas détaillés)

Ce sont les étapes facultatives ou alternatives à celles du scénario nominal. Il n'est pas nécessaire de les exécuter pour que le cas s ecomplète avec un succès. Pour chaque extention, on lui assigne un code basé sur l'étape à laquelle l'extension peut s'exécuter. Si plusieurs extensions peuvent se produire à la même étape, on ajoute une lettre minuscule, en ordre alphabétique, pour les différencier. Si l'extension peut se produire à plusieurs ou toutes les étapes, on utilise le * plutôt qu'un numéro d'étape. On décrit ensuite de façon détaillée (souvent en liste) les étapes pour accomplir l'extention.

On considère que le scénario nominal continu ensuite avec la prochaine étape. Si ce n'est pas le cas, il faut le préciser clairement.

spécification non fonctionnel (section optionnelle)
On indique les éléments à tenir compte dans la conception du cas, mais qui ne correspondent pas à des étapes du fil d'exécution du système. On y trouve des particularités sur l'interface du système, des contraintes de temps d'exécution ou de journalisation. Tout autre spécification non fonctionnelle peut s'y retrouver.
diagramme de séquence système (section optionnelle)
Si le cas présente une structure complexe, on peut ajouter un diagramme de séquence système basé sur le scénario nominal et les extensions. On ne fait pas de diagramme s'il y a peu ou aucune extension ou que le diagramme à l'air d'une échelle. Il faut aussi se souvenir qu'un diagramme demande d'être mis à jour lorsque les spcéfications évoluent.
diagramme d'état-transition (section optionnelle)
Si le cas présente une structure complexe où l'état d'un objet change selon plusieurs conditions, on peut ajouter un diagramme d'états-transitions pour modéliser ces transition. C'est le genre de diagramme qui s'inclut bien dans un cas englobant. Si les changements d'états sont peu nombreux ou se font selon des conditions simples, il n'est pas nécessaire d'inclure ce diagramme. Il faut aussi se souvenir qu'un diagramme demande d'être mis à jour lorsque les spcéfications évoluent.
prototype d'écran ou diagramme en fil de fer
Le prorotype d'écran présente les contrôles et le fonctionnement de l'interface (lien entre les boutons et les rétroactions). On n'inclut pas d'élément de mise en forme dans ces prototypes, on se concentre sur l'utilisabilité de l'interface. Il seront décrits en détail dans la section sur les interfaces utilisateurs.

Trucs dans l'écriture des cas d'utilisation

Ne pas copier-coller d'information
Le copier-coller d'information entraîne la duplication de l'information et il devient nécessaire de dupliquer chacune des modifications qui occurent. Comme il est impossible de se souvenir de toutes les duplications qui ont été faites, on préfère faire référence en indiquant de façon souligné le nom du CU. Cela évite d'avoir plusieurs versions de la même spécifications qui se contredisent entre elles.
Éviter de « sauver des étapes »
Abréger des CU long en évitant d'écrire des étapes simples peut mener à les oublier (par exemple une validation avant de quitter une page). Donc même si certaines étapes semblent superflues, il faut se souvernir que les descriptions peuvent être consultées des mois après leur écriture. Donc une spécification qui parait superflue aujourd'hui peut rapidement nous sortir de la tête et devenir un oubli quelques semaines plus tard...
Rassembler des spécifications ou faire des cas englobant
Cette technique d'écriture permet de contourner le problème des copier-coller et des références trop nombreuses. En incluant une section de « spécification non fonctionnelles » globale et en déplaçant certains éléments descriptifs vers un cas englobant, cela simplifie chacun des sous-cas et réduit les redondences.
