    Distinguer fonctionnalités et cas d'utilisation

    Une fonctionnalité est une opération que l'on peut accomplir avec le système. Elle est généralement de petite envergure et est centrée sur la capacité du système à accomplir quelque chose. Un cas d'utilisation est une interaction entre le système et une personne utilisatrice qui peut inclure la manipulation de plusieurs fonctionnalités.

    À noter également qu'une fonctionnalité peut être incluse dans plusieurs cas d'utilisation.

    Identifier les cas d'utilisation

    Deux sources d'informations principales permettent

    1. l'identification des cas d'utilisation à partir des récits utilisateurs;
    2. l'identification de besoins non fonctionnels liés à des groupes de personnes utilisatrices (persona)

    Pour l'identification des cas d'utilisation, on énumère des fonctionnalités que le système doit posséder ou des actions que l'on doit pouvoir accomplir avec ce dernier. Pour déterminer si une fonctionnalité ou action constitue un cas d'utilisation (CU), on lui fait subir trois tests :

    • Test du patron : est-ce que votre patron est content que vous investissiez du temps dans cette tâche ? Ce test rejette bon nombre de cas trop simples comme simplement cocher une case ou remplir un champ. La majorité des CU implique une modification de plusieurs champs ou une utilisation potentielle de plusieurs contrôles ou de plusieurs fonctionnalités.
    • Test d'un processus métier élémentaire (PME) : est-ce le CU est ciblé sur une tâche métier élémentaire. Une tâche métier élémentaire est une action pour laquelle on peut observer la réalisation (donc qui exclut les grands énoncés vagues) et se réalise de façon relativement concise et cohérente. Par exemple, « Répondre aux besoins du client » n'est pas un PME, car il s'agit d'un grand énoncé sans résultat toujours observable. L'action de « Gérer le compte d'un client » échoue également le test, car ce n'est pas concis et précis (donc élémentaire), même si toutes les opérations de gestion d'un compte (création, suspension, renouvellement...) produisent un résultat observable. « Effectuer le paiement d'un solde à un compte client » en est un, car c'est observable comme résultat et concis, et ce, même si l'action en elle-même se divise en plus petites actions.
    • Test de la taille : est-ce que votre cas correspond à une opération ? Autrement dit, est-ce que cette action est simple, toujours effectuée en combinaison avec d'autres actions ou représente simplement un cas particulier d'une action plus large. Par exemple « Remplir le prénom » d'un formulaire d'abonnement est une opération, car on l'accomplit toujours en saisissant le formulaire d'abonnement. Il ne s'agit donc pas d'un CU. Par contre, « Payer l'abonnement », même si l'opération s'effectue toujours après avoir saisi le formulaire d'abonnement n'est pas une action simple, donc constitue un CU à part entière.

    Critères à respecter

    Il se peut durant les discussions que des critères à respecter soient énoncés plutôt que des actions offertes dans le système. Il peut s'agir d'éléments à inclure dans les tests d'acceptation. Nous traiterons cet aspect dans la section sur les tests d'acceptation.

    Ne pas respecter les tests

    Il arrive qu'il soit pertinent de faire un CU qui ne respecte pas les tests. Cette décision doit s'appuyer sur des éléments raisonnables (« c'est trop long, ça ne me tente pas, je manque de temps » ne sont pas des éléments raisonnables).

    Souvent, on utilise comme une raison la possibilité de réutiliser une opération pour justifier des CU qui seraient autrement trop petits. Il faut que la réutilisation soit évidente et qu'elle soit employée (autrement vous allez embourber votre projet de CU trop petits). Le piège dans ce raisonnement est d'isolé une action dans un CU au cas pour pouvoir la réutiliser, mais la réutiliser qu'une seule fois...

    Grouper des CU

    Il arrive que pour des fins de clareté, il soit pertinent de grouper des CU pour simplifier la compréhension du système. Généralement, ces groupements vont êter le forme « gérer » un type de donnée. La gestion va ressembler à un CRUD :

    Étape Nom Rôle Verbe dans le titre du CU
    C Créer (create) Ajouter les données dans le système. Sans une opération de ce type, les données doivent être préexistante dans le système ce qui est très limitatif. Créer, Importer, Ajouter, Lier...
    R Lire (read) Affiche les données pertinentes. Généralement ces cas sont simples et servent à se déplacer entre les interfaces. Parfois, on peut inclure ce cas dans un autre, comme modifier. Lister, Sélectionner, Afficher les détails, Exporter...
    U Modifier (update) Modifie les données existantes. Il est important de permettre la modification du plus grand nombre de données possibles, même si ce n'est que pour corriger les erreurs lors de la création. Mettre à jour...
    D Supprimer (delete) Retire une donnée du système. Généralement on ne peut directement supprimer une donnée. On trouve souvent des systèmes d'innactivité ou d'archivage. Supprimer, retirer, archiver, marquer comme innactif...

    Artéfacts des cas d'utilisation

    Les cas d'utilisation sont l'une des techniques les plus utilisées pour exprimer des besoins logiciels. Plusieurs méthodes pour les décrire ont été proposées, certaines plus visuelles, d'autres plus textuelles. Ce qu'il faut retenir c'est que la description textuelle a toujours plus d'utilité qu'un diagramme. C'est donc là que l'effort principal doit être mis. Tous les éléments présents sur les diagrammes devraient se retrouver dans la description textuelle. Les diagrammes appuient les textes en synthétisant des informations détaillées sur une seule image; ils appuient le texte et non l'inverse.

    Lors de l'itération 0, tout ce qui est à faire est de nommer les cas d'utilisation possibles et les fonctionnalités. Le détail de chacun sera traité à partir de l'itération 1.

    Liste des cas d'utilisation

    La liste des cas, comme son nom l'indique liste tous les CU du système. On regroupe les cas par « proximité » de fonctionnalité afin d'éviter d'avoir une liste désorganisée. Également, pour chaque CU, on lui assigne un code qui peut être aussi simple qu'un numéro séquentiel ou être un système de référencement plus complexe. Les entités actrices intervenant dans le CU sont aussi indiquées.

    Diagramme des cas d'utilisation

    Le diagramme des cas d'utilisation permet de représenter graphiquement les CU et les entités actrices, ainsi que les relations qui les lient. On peut, si le système comporte de nombreux CU, limiter la représentation graphique aux CU groupés.
