    Pipeline de développement

    Contenus de la page

    3-7 Mise en application pratique de l'ensemble des principes d’une méthode d’analyse
    3-8 Étapes de développement d'un projet

    Temps requis

    20 minutes

    À propos de la page

    Signaler une erreur

    L'usage d'un pipeline de développement permet d'automatiser les activités connexes au développement en augmentant la vitesse de travail par l'éliminitation des opérations répétitives.

    Avec un pipeline comme celui-ci, quelques clics permettent d'avoir un système prêt à l'emploi. Si par exemple on avait un site web, on pourrait simplement ajouter une étape pour effectuer une mise à jour du serveur. On appelle le développement de ces pipelines le devops (collaboration développement et opération).

    Toutefois, la détermination des étapes et souvent la configuration des outils demeurent un travail humain. Les IA agentiques supportent de mieux en mieux les processus, mais comme toutes les tâches de haut niveau, dès que vous vous éloignez d'une solution toute faite ou qu'il y a des changements récents, les IA sont moins performantes. Dans de grandes équipes, il peut y avoir des personnes dont l'unique travail est de gérer le devops.

    Exemple de pipeline typique et simple

    Analysons le pipeline proposé :

    1. Compilation locale avec Gradle

    Gradle est un système d'automatisation avec les technologies Java, il remplit un rôle similaire à celui que remplit NPM. Avec ce système, il est possible de standardiser la configuration de compilation et gérer les dépendances. Les fichiers Gradle ne sont habituellement pas partagés, toutefois il faut s'assurer que les configurations sont communes.

    En savoir plus sur Gradle.

    2. Tests avec Gradle

    Selon la tâche Gradle effectuée, il est possible d'effectuer tous les tests chargés dans l'environnement local. C'est une bonne pratique pour éviter de publier des versions contenant des bogues. Toutefois, tous les bogues ne se manifestent pas nécessairement dans l'environnement local.

    3. Commit

    Une fois qu'une version est fonctionnelle on la publie sur Git, d'abord en locale puis on peut la partager sur le distant. Afin d'assurer un versionnage clair, il est important que les versions avec des commits publiés soient exemptes d'erreurs.

    4. La pull-request (PR)

    Ensuite, lorsqu'une fonctionnalité est prête à être intégrée au projet, donc qu'elle est exempte d'erreur, mais pas nécessairement complétée. La PR idéale fait entre 200 et 400 lignes de code. Plus une équipe est performante, plus ses PR sont de petite taille.

    En savoir plus sur Git Hub et les pull-requests.

    Revue de code par IA

    De plus en plus on ajoute l'IA comme revue de code à l'étape de la PR. Cette pratique permet entre autres de révéler des standards de code non respecté et certaines failles de sécurité. Toutefois, l'alignement des objectifs du projet n'est pas toujours bien compris par l'IA, donc il faut rester vigilant sur les changements proposés pour ne pas dégrader le projet.

    5. Tests distants et automatisation

    Ensuite, une série de tâches préprogrammées, dont l'exécution des tests, s'effectue sur le code afin d'assurer sa validité. Les tests sont les mêmes que ceux en locaux, mais parfois l'exécution sur le serveur permet de révéler certaines erreurs. Également, ça empêche le code d'être intégré tant qu'il brise quelque chose dans le projet.

    6. Déploiement

    Finalement, par automatisation on déploie automatiquement la nouvelle version du projet. Dans le cadre du cours, cela sera simplement l'ajout d'un tag qui augmente le numéro de build du projet.

    Ajustements au pipeline et autres tâches

    Un pipeline n'est efficace que s'il répond aux besoins de l'équipe. Dans ce cas, il est important de l'adapter aux opérations que l'on fait au fur et à mesure. Aussi, d'autres tâches peuvent intervenir dans le pipeline, par exemple celles pour maintenir à jour l'information du tableau de bord du projet.
