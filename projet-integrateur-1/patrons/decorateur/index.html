Décorateur (Decorator)

Personnes autrices : Ahmed Ali El Amri et Marwa EL HOUADI
Cours : 420-5B5-VI — Projet intégrateur 1

Le problème : les combinaisons de classes

Un café propose deux boissons de base : un espresso et un café filtre. Le client peut ajouter du lait, du sirop d'érable ou de la crème fouettée.

Une première approche serait de créer une classe pour chaque combinaison : CafeFiltreLait, CafeFiltreSirop, CafeFiltreLaitSirop, etc.

Avec deux boissons et trois ingrédients présents zéro ou une fois, on obtient 2 × 2³ = 16 variantes concrètes, en comptant les boissons sans ajout.

Si on ajoute un ingrédient ou si on veut deux portions de sirop, il faut prévoir davantage de variantes. Cette approche devient difficile à maintenir.

Le patron Décorateur permet de construire ces combinaisons à partir de classes réutilisables.

Fonctionnement du patron

Le Décorateur est un patron de conception de structure. Il permet d'ajouter des responsabilités à un objet à l'exécution, sans modifier sa classe (Gamma et al., 1994).

Son principe est l'enveloppement. Un décorateur conserve une référence vers l'objet qu'il décore. Il appelle les méthodes de cet objet et ajoute son propre comportement avant ou après l'appel.

Le composant et ses décorateurs respectent la même interface. Un décorateur peut donc envelopper un composant de base ou un autre décorateur. Les objets s'imbriquent comme des poupées russes.

Dans notre exemple, on crée un café filtre. Le décorateur Lait enveloppe ce café, puis SiropErable enveloppe le résultat. La classe CafeFiltre conserve son code.

Les participants

Participant Rôle
Composant Interface qui définit les opérations communes aux objets de base et aux décorateurs.
ComposantConcret Classe de l'objet de base auquel on veut ajouter un comportement.

Dans le diagramme :

  • La réalisation d'une interface utilise une flèche pointillée avec un triangle vide.
  • La généralisation, utilisée pour l'héritage, utilise une flèche pleine avec un triangle vide.
  • Le lien du décorateur vers le composant représente la référence vers l'objet enveloppé.

Comment les classes travaillent ensemble

Dans notre implémentation C# :

  • IBoisson définit les méthodes communes Description() et Cout().
  • CafeFiltre et Espresso représentent les boissons de base et implémentent IBoisson.
  • DecorateurBoisson est une classe abstraite qui implémente aussi IBoisson. Elle conserve la boisson à décorer dans un attribut.
  • Lait, SiropErable et CremeFouettee héritent de DecorateurBoisson. Chaque décorateur appelle les méthodes de la boisson enveloppée, puis ajoute sa description et son supplément.
  • Afficher(IBoisson boisson) peut recevoir une boisson simple ou une boisson décorée.

Par exemple, la méthode suivante appartient à Lait :

public override double Cout() => boisson.Cout() + 0.60;

boisson.Cout() demande le coût à l'objet enveloppé. C'est la délégation. Le décorateur ajoute ensuite son supplément de 0,60 $ au résultat.

Le fait de conserver une boisson dans un décorateur correspond à la composition d'objets.

L'héritage permet ici à Lait, SiropErable et CremeFouettee de partager le code de leur base DecorateurBoisson.

Le champ boisson est protected readonly dans le code C#. Les décorateurs dérivés peuvent l'utiliser, mais le programme client ne peut pas y accéder directement. La référence est fixée pendant la construction de l'objet.

Le code qui construit la boisson choisit les classes concrètes. Une fois la combinaison créée, la méthode Afficher() utilise seulement les opérations de IBoisson. Elle n'a pas besoin de connaître les ingrédients présents.

C'est le polymorphisme : Afficher() appelle Cout() et Description() de la même façon, que la boisson soit un CafeFiltre, un Espresso ou une boisson décorée. Chaque classe exécute sa propre version de ces méthodes.

Les concepts de la POO dans notre exemple

Concept de la POO Où on le voit dans notre exemple
Abstraction IBoisson et la classe abstraite DecorateurBoisson définissent ce que fait une boisson sans imposer comment.
Polymorphisme Afficher(IBoisson) traite de la même façon un CafeFiltre, un Espresso ou une boisson décorée. Chaque classe fournit sa version.
Héritage Lait, SiropErable et CremeFouettee héritent de DecorateurBoisson et partagent son code.
Redéfinition (override) virtual dans DecorateurBoisson, override dans les décorateurs concrets.
Composition Chaque décorateur contient une IBoisson, par exemple Lait contient un CafeFiltre.
Délégation boisson.Cout() transmet l'appel à l'objet enveloppé, puis le décorateur ajoute son supplément.
Encapsulation Le champ boisson est protected readonly : les classes dérivées l'utilisent, mais le client n'y a pas accès.

Notre exemple : les boissons au café

Les prix

Boisson ou ingrédient Prix

Construire une boisson

IBoisson boisson = new SiropErable(new Lait(new CafeFiltre()));

La construction se lit de l'intérieur vers l'extérieur :

  1. new CafeFiltre() crée la boisson de base.
  2. new Lait(...) crée un décorateur autour du café.
  3. new SiropErable(...) crée un décorateur autour du café déjà décoré avec du lait.

On peut écrire la même construction en plusieurs instructions :

IBoisson boisson = new CafeFiltre();
boisson = new Lait(boisson);
boisson = new SiropErable(boisson);

Calculer le coût

Quand le client appelle Cout() sur le décorateur extérieur, le calcul suit les étapes suivantes :

  1. SiropErable appelle Cout() sur le Lait qu'il contient.
  2. Lait appelle Cout() sur le CafeFiltre qu'il contient.
  3. CafeFiltre retourne 2,00 $.
  4. Lait ajoute 0,60 $ et retourne 2,60 $.
  5. SiropErable ajoute 0,75 $ et retourne 3,35 $.

La description suit le même chemin. Chaque décorateur complète le texte de l'objet enveloppé.

Le programme affiche :

Café filtre, lait, sirop d'érable : 3.35 $

Le point décimal provient du format d'affichage choisi dans les programmes.

L'implémentation en C# et JavaScript

Les deux programmes utilisent les mêmes boissons, les mêmes ingrédients et la même logique.

La façon de déclarer les méthodes et l'interface change selon le langage.

Exemple en C

En C#, IBoisson est une interface explicite. Le compilateur vérifie que les classes fournissent les méthodes demandées.

La classe DecorateurBoisson est abstract : on ne peut pas l'instancier directement.

Ses méthodes sont virtual pour permettre aux décorateurs concrets de les redéfinir avec override.

L'extrait suivant montre le café filtre avec du lait et du sirop. Il peut être exécuté dans le fichier Program.cs d'un projet console distinct.

Dans notre dépôt, les classes sont réparties dans leurs propres fichiers.

using System;
using System.Globalization;

public interface IBoisson
{
    string Description();
    double Cout();
}

public class CafeFiltre : IBoisson
{
    public string Description() => "Café filtre";

    public double Cout() => 2.00;
}

public abstract class DecorateurBoisson : IBoisson
{
    protected readonly IBoisson boisson;

    protected DecorateurBoisson(IBoisson boisson)
    {
        this.boisson = boisson;
    }

    public virtual string Description() => boisson.Description();

    public virtual double Cout() => boisson.Cout();
}

public class Lait : DecorateurBoisson
{
    public Lait(IBoisson boisson) : base(boisson) { }

    public override string Description()
        => $"{boisson.Description()}, lait";

    public override double Cout()
        => boisson.Cout() + 0.60;
}

public class SiropErable : DecorateurBoisson
{
    public SiropErable(IBoisson boisson) : base(boisson) { }

    public override string Description()
        => $"{boisson.Description()}, sirop d'érable";

    public override double Cout()
        => boisson.Cout() + 0.75;
}

public static class Program
{
    public static void Main()
    {
        IBoisson boisson = new SiropErable(
            new Lait(new CafeFiltre())
        );

        string prix = boisson.Cout().ToString(
            "F2",
            CultureInfo.InvariantCulture
        );

        Console.WriteLine($"{boisson.Description()} : {prix} $");
    }
}

Exemple en JavaScript

JavaScript permet de définir des classes, mais ne déclare pas d'interface IBoisson comme en C#.

Les boissons et les décorateurs proposent les mêmes méthodes : description() et cout().

Les sous-classes redéfinissent les méthodes en utilisant les mêmes noms, sans le mot-clé override.

Dans notre exemple, le constructeur vérifie new.target pour empêcher l'instanciation directe de DecorateurBoisson. Cette vérification ne contrôle pas les méthodes de l'objet reçu.

Les commentaires JSDoc peuvent documenter les méthodes attendues, mais ne créent pas une interface imposée par le moteur JavaScript.

L'extrait suivant utilise les modules ES, comme le dépôt d'Ali. Il peut être exécuté dans un fichier .mjs ou dans un projet dont le package.json contient "type": "module".

/**
 * Méthodes communes aux boissons et aux décorateurs.
 * @typedef {Object} IBoisson
 * @property {function(): string} description
 * @property {function(): number} cout
 */

export class CafeFiltre {
  description() {
    return 'Café filtre';
  }

  cout() {
    return 2.0;
  }
}

export class DecorateurBoisson {
  /** @param {IBoisson} boisson */
  constructor(boisson) {
    if (new.target === DecorateurBoisson) {
      throw new TypeError(
        'DecorateurBoisson ne peut pas être instanciée directement.',
      );
    }

    this.boisson = boisson;
  }

  description() {
    return this.boisson.description();
  }

  cout() {
    return this.boisson.cout();
  }
}

export class Lait extends DecorateurBoisson {
  description() {
    return `${this.boisson.description()}, lait`;
  }

  cout() {
    return this.boisson.cout() + 0.6;
  }
}

export class SiropErable extends DecorateurBoisson {
  description() {
    return `${this.boisson.description()}, sirop d'érable`;
  }

  cout() {
    return this.boisson.cout() + 0.75;
  }
}

const boisson = new SiropErable(new Lait(new CafeFiltre()));

console.log(`${boisson.description()} : ${boisson.cout().toFixed(2)} $`);

Comparaison des langages

Élément C# JavaScript de notre exemple
Méthodes communes Définies par l'interface IBoisson Présentes dans les objets, sans interface déclarée
Base du décorateur Classe abstract Classe dont le constructeur interdit l'instanciation directe
Redéfinition des méthodes virtual dans la base et override dans les sous-classes Méthodes de même nom dans les sous-classes
Référence vers la boisson Champ protected readonly Champ public boisson
Noms des méthodes Description() et Cout() description() et cout()

Le compilateur C# vérifie le respect de l'interface et les redéfinitions.

En JavaScript, l'objet reçu doit proposer les méthodes appelées. Si une méthode manque, l'appel provoque une erreur à l'exécution.

Résultats des programmes complets

Les deux programmes complets affichent :

Espresso : 2.50 $
Café filtre, lait, sirop d'érable : 3.35 $
Espresso, sirop d'érable, crème fouettée : 4.15 $
Café filtre, lait, sirop d'érable, sirop d'érable : 4.10 $

Le dernier exemple applique deux fois SiropErable.

On réutilise la même classe pour ajouter une deuxième portion :

IBoisson boisson = new SiropErable(
    new SiropErable(
        new Lait(new CafeFiltre())
    )
);

Le total est :

2,00 $ + 0,60 $ + 0,75 $ + 0,75 $ = 4,10 $

Avantages et limites

Avantages

Avantage Explication dans notre exemple
Responsabilités séparées Chaque décorateur gère un ingrédient et son supplément.
Combinaisons à l'exécution On choisit les objets à assembler selon la boisson demandée.
Décorateurs réutilisables Lait fonctionne avec un CafeFiltre, un Espresso ou une boisson déjà décorée.
Extension sans modifier les boissons existantes Un nouveau décorateur Caramel peut être ajouté, puis utilisé dans l'assemblage.
Utilisation commune Afficher() utilise les mêmes méthodes pour une boisson simple ou décorée.

Limites

Limite Explication
Plusieurs petites classes Le projet contient une classe par type de décorateur.
Assemblage parfois difficile à lire Plusieurs constructions new imbriquées peuvent compliquer la lecture. On peut les séparer en plusieurs instructions.
Ordre parfois significatif Dans le café, l'ordre change la description, mais pas le total. Dans d'autres usages, il peut aussi changer le traitement.
Retrait d'une couche peu pratique Enlever un décorateur au milieu de la chaîne demande souvent de reconstruire la combinaison.
Débogage d'une chaîne d'appels Un appel ou une exception peut traverser plusieurs objets avant de revenir au client.

L'enveloppe et l'objet enveloppé sont deux objets distincts. Il faut donc éviter de supposer qu'ils ont la même identité ou le même type concret.

Une interface commune limitée aux opérations utiles facilite aussi l'écriture des décorateurs.

Impact sur les bonnes pratiques de conception

Les avantages et les limites précédents ont des conséquences sur quatre bonnes pratiques de conception de logiciels : la modularité, la réutilisabilité, la lisibilité et la limitation de la propagation des erreurs.

Bonne pratique Conséquence positive Conséquence négative
Modularité Chaque classe a une seule responsabilité : Lait gère le lait, SiropErable gère le sirop. On les modifie ou on les teste séparément. Le nombre de classes augmente : une classe par ingrédient et par boisson de base.
Réutilisabilité Lait fonctionne avec CafeFiltre, Espresso ou une boisson déjà décorée, et on peut l'utiliser plusieurs fois (deux portions de sirop). Tous les décorateurs dépendent de IBoisson. Un changement dans l'interface oblige à modifier toutes les classes.
Lisibilité Chaque classe est courte et son nom indique son rôle. Le code qui utilise la boisson ne change pas, qu'elle soit simple ou décorée. Les new imbriqués sont difficiles à lire, et il faut suivre la chaîne d'objets pour savoir ce qu'une boisson contient.
Limitation de la propagation des erreurs Ajouter Caramel ne modifie pas CafeFiltre ni les autres décorateurs. Le code déjà testé n'est pas touché, donc le risque d'introduire une erreur diminue. Une exception traverse toute la chaîne avant d'atteindre le client. Un décorateur qui oublie de déléguer l'appel donne un résultat faux sans signaler d'erreur.

Quand utiliser le Décorateur ?

Le Décorateur est utile pour ajouter des fonctionnalités optionnelles à un objet et les combiner sans modifier sa classe.

  • Personnalisation : ajouter du lait ou du sirop à une boisson.
  • Journalisation : enregistrer une trace des appels à une méthode, par exemple avant et après son exécution.
  • Cache : conserver un résultat et le réutiliser lorsqu'une demande équivalente revient, pour éviter de refaire le calcul.
  • Validation : vérifier les données avant de transmettre l'appel au traitement, selon les règles prévues par l'interface.

Chaque fonctionnalité peut être placée dans un décorateur distinct.

On conserve le même principe : l'objet extérieur appelle l'objet enveloppé et complète son comportement.

Ce patron convient surtout lorsque les ajouts doivent être combinés de plusieurs façons. Pour une seule fonctionnalité fixe, une structure plus simple peut suffire.

Conclusion

Le Décorateur enveloppe un composant pour ajouter un comportement.

Le composant et ses décorateurs respectent une interface commune, ce qui permet de les empiler.

Dans notre exemple C#, les boissons et les décorateurs utilisent IBoisson. La composition permet de combiner les ingrédients à l'exécution.

Chaque décorateur délègue les appels à la boisson qu'il contient, puis ajoute sa contribution à la description et au prix.
