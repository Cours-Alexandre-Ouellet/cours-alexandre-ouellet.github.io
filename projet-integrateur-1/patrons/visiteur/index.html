Visiteur¶

Personne autrice : Leah Kungne Wabo, Ben Schalom Kamga
Patrons liés : Composite, Itérateur, Commande

Fonctionnement du patron¶

Appartenant à la catégorie comportementale, le patron Visiteur sépare les algorithmes des objets sur lesquels ils opèrent. Il permet d'ajouter de nouvelles opérations à une structure d'objets sans modifier les classes de ces objet.

Les acteurs du patron

Son fonctionnement repose sur cinq acteurs :

  • Visiteur : l'interface qui déclare une méthode de visite par type d'élément concret. Elles peuvent avoir le même nom dans le cas où elles sont écrites dans un language qui supporte la surchage cependant, le type du paramètre doit être unique à chaque surcharge et correspondre aux types des objets de la structure.
  • VisiteurConcret : Implemente chacune des methodes définis dans le visiteur. Il aurra donc plusieurs versions du même comportement en fonction du type des objets de la structure.
  • Élément : Interface qui qui declare une méthode d'acceptaiton des visiteurs et dont le type du paramètre est celui de l'interface visiteur.
  • ÉlémentConcret : Implémente la méthode d'acceptation définis dans l'interface élément et dont le but est de rediriger l'appel vers la méthode appropriée du visiteur en fonction de la classe de l'élément actuel.
  • Client : qui celui qui possède la structure d’objets et qui lance un visiteur dessus.

Le cœur du patron : la double répartition (double dispatch)

Lors d'un appel normal, une seule chose décide de la méthode exécutée : le type de l'objet sur lequel on appelle.

Le mécanisme se fait en deux temps. D'abord, l'élément concret exécute la méthode d'acceptation, c'est lui grace à son type qui choisira la bonne méthode du visiteur. Ensuite, c’est le visiteur réellement passé qui s’exécute : son type à lui détermine le traitement appliqué. Deux appels, deux choix successifs: l’un sur le type de l’élément, l’autre sur le type du visiteur d'où le nom double répartition. Ce mécanisme mobilise l'abstraction (les deux interfaces) et le polymorphisme (chaque appel se dirige vers la bonne implémentation).

Avantages et désavantages du patron¶

Avantages

  • Principe ouvert/fermé : on peut ajouter un nouveau comportement qui agit sur les objets de différentes classes sans modifier ces classes.
  • Principe de responsabilité unique : les différentes variantes d'un même comportement sont regroupées dans une seule classe, au lieu d'être dispersées dans la structure.
  • Un visiteur peut accumuler de l'information pendant le parcours d'une structure complexe (par exemple compter des éléments).

Désavantages

  • Il faut mettre à jour tous les visiteurs chaque fois qu'une classe est ajoutée ou retirée de la hiérarchie des éléments.
  • Un visiteur n'a parfois pas accès aux attributs ou méthodes privés des éléments qu'il doit manipuler, ce qui peut obliger à réduire l'encapsulation.

Exemple d'utilisation¶

Le contexte et le problème

Reprenons la navigation d'un site web, composée de menus et d'options. La structure est en place, mais au fil du temps on doit lui appliquer différentes actions : désactiver une section, afficher l'arborescence, exporter le menu, et ainsi de suite.

Vu la taille du système, il n'est pas recommandé de modifier les classes Menu et Option (déjà utilisées et testées). De plus, certaines actions, comme l'export, n'ont pas vraiment leur place à l'intérieur de ces classes : leur rôle est de représenter la navigation, pas de connaître un format d'export.

La solution avec Visiteur

On sort chaque action des classes et on la place dans un visiteur séparé. Les éléments Menu et Option se contentent d'accueillir un visiteur par une méthode accept(), et chacun indique au visiteur la méthode à exécuter pour son propre type. Ajouter une action revient alors à créer une nouvelle classe de visiteur, sans jamais toucher à Menu ni à Option.

// Interface Visiteur : une méthode de visite par type d'élément.
class IVisiteur {
    visitMenu(menu) { throw new Error("visitMenu() doit être implémentée"); }
    visitOption(option) { throw new Error("visitOption() doit être implémentée"); }
}

module.exports = IVisiteur;

const IComposantMenu = require("./icomposant-menu");

// Élément concret (A): Implemente la methode d'acceptation définis dans l'interface élément.
class Option extends IComposantMenu {
    constructor(nom, actif = true) {
        super();
        this.nom = nom;
        this.actif = actif;
    }

    //Implementation de l'interface element
    accept(visiteur) {
        visiteur.visitOption(this);
    }
}

module.exports = Option;

const IComposantMenu = require("./icomposant-menu");

// Élément concret (B) : Implemente la methode d'acceptation définis dans l'interface élément.
class Menu extends IComposantMenu {
    constructor(nom, actif = true) {
        super();
        this.nom = nom;
        this.actif = actif;
        this.enfants = [];
    }

    ajouter(enfant) {
        this.enfants.push(enfant);
    }

    //Implementation de l'interface element
    accept(visiteur) {
        visiteur.visitMenu(this);      
        for (const enfant of this.enfants) {
            enfant.accept(visiteur);    
        }
    }
}

module.exports = Menu;

const IVisiteur = require("./ivisiteur");

// Chaque opération est un visiteur concret,
class DesactiverVisiteur extends IVisiteur {
    visitOption(option) { option.actif = false; }
    visitMenu(menu) { menu.actif = false; }
}

module.exports = { DesactiverVisiteur};
