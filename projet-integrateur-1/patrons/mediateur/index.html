Patron Médiateur

Personnes autrices : Didier Mathieu, Christine Lehoux
Patrons liés : Observateur, Façade, Commandes

Fonctionnement du patron

Le patron Médiateur (Mediator) est un patron de conception comportemental. Il sert à réduire les dépendances directes et chaotiques entre les objets en les obligeant à communiquer uniquement par l'intermédiaire d'un objet central (le médiateur).

Les différents composants :

  • Médiateur (interface) : Définit les méthodes permettant aux composants de communiquer avec le médiateur et de lui signaler des actions.

  • Médiateur concret : gère les échanges entre les composants en recevant leurs notifications et en décidant des actions à exécuter.

  • Composant (classe abstraite) : représente un élément du système qui possède une référence vers le médiateur pour communiquer avec lui.

  • Composants concrets : représente les éléments spécifiques du système, comme les champs textes, les boutons ou des cases à cocher. Ils signalent au médiateur leurs événements. Ils ignorent totalement l'existence des autres composants.

Concepts de programmation orientée objet mobilisés

Le patron Médiateur utilise des concepts de la programmation orientée objet pour permettre aux composants de communiquer sans dépendre directement les uns des autres. Un objet central, le médiateur, coordonne leurs échanges et réduit les liens entre les classes.

Les interfaces et les classes abstraites ne sont pas obligatoires, mais elles sont souvent utilisées dans la forme classique du patron (voir le diagramme). Elles rendent le code plus flexible. Le patron permet aussi de réutiliser des classes existantes sans devoir utiliser l'héritage.

  • Abstraction (facultative) : dans la forme classique, une interface déclare ce que le médiateur doit offrir, généralement une seule méthode de notification, et une classe de base représente ce que les composants ont en commun. Ces abstractions ne sont pas obligatoires. Sans elles, chaque composant peut déclarer lui-même sa référence vers le médiateur.

  • Encapsulation : le médiateur encapsule les relations complexes entre les composants et chaque composant est vu comme une boîte noire par les autres. Un composant ne connaît donc ni les autres composants ni leur fonctionnement interne. Il signale seulement un événement au médiateur. La référence vers le médiateur est aussi protégée.

  • Héritage (facultatif) : les composants concrets héritent d'une classe de base qui contient la référence vers le médiateur. Sans la classe de base, chaque composant garde sa propre référence vers le médiateur.

  • Polymorphisme : un composant utilise l'interface du médiateur plutôt que de dépendre d'une classe précise. Il peut donc fonctionner avec différents médiateurs sans avoir à modifier son code. L'utilisation d'interfaces facilite également les tests.

  • Association et agrégation : les composants gardent une référence vers le médiateur, et lui, conserve des références vers les composants qu'il gère. Il peut même s'occuper de leur création et de leur destruction, ce qui devient alors une composition et ressemble à une fabrique (autre patron).

  • Délégation : lorsque le médiateur reçoit une notification, il peut traiter la demande lui-même ou demander aux composants concernés d'effectuer les actions nécessaires.

  • Injection de dépendances : le médiateur peut être fourni à un composant par son constructeur lors de sa création ou lui être attribué par la suite.

Avantages et désavantages du patron

Avantages

  • Principe de responsabilité unique : permet de centraliser les communications entre différents composants en un seul endroit, rendant le code plus clair et plus facile à comprendre et à maintenir.

  • Principe ouvert/fermé : permet d'ajouter de nouveaux médiateurs (ou de modifier ceux existants) sans avoir à toucher aux composants.

  • Réduction du couplage : permet de réduire les liaisons directes et chaotiques entre les différents composants d'un système.

  • Réutilisation accrue : permet de réutiliser plus facilement les composants dans d'autres systèmes, puisqu'ils ne dépendent pas directement les uns des autres.

Désavantages

  • Dépendance du médiateur : si le médiateur brise, tout le programme brise, car toutes les dépendances proviennent du médiateur en lui-même.

  • Temps de planification : il faut bien prendre le temps de tout connecter au médiateur pour ne pas faire d'erreur, car le médiateur est un composant très complexe. Chacun des composants a besoin de savoir les règles du médiateur.

  • Lenteur du programme : le médiateur peut être plus lent, car il y a une grande augmentation de la dépendance sur le médiateur.

  • Objet omniscient : le médiateur peut évoluer en un objet qui reconnaît trop de choses ou qui fait trop de choses si le système est complexe.

Situations où le patron est pertinent

Le patron Médiateur est utile lorsque des objets doivent collaborer, mais que leurs liens deviennent trop complexes et causent le code à être difficile à comprendre et à modifier.

Le médiateur est pertinent lorsque :

  • Plusieurs classes dépendent étroitement les unes des autres. Modifier l'une oblige à changer les autres.

  • Un composant est difficile à réutiliser ailleurs, parce qu'il dépend trop des autres.

  • On veut ajouter ou changer des interactions sans modifier les composants.

Exemples de situations typiques :

  • Interface graphique : une boîte de dialogue dont les composants s'influencent (exemple : activer un bouton seulement si un champ texte est rempli).

  • Salon de clavardage ou tour de contrôle : des participants qui échangent par un point central plutôt que directement entre eux (exemple : pilotes qui contactent la tour de contrôle au lieu des autres pilotes).

Il est moins pertinent lorsque le système compte seulement quelques objets avec des interactions simples. Le médiateur ajouterait alors une complexité inutile.

Exemple d'utilisation

Dans une maison intelligente, plusieurs appareils peuvent interagir entre eux pour automatiser certaines tâches quotidiennes. Par exemple, lorsqu'un détecteur de mouvement repère une personne dans une pièce, il peut demander l'allumage d'une ampoule. Sans le patron médiateur, le détecteur devrait connaître directement l'ampoule pour communiquer avec elle. En utilisant ce patron, les appareils communiquent plutôt par l'intermédiaire d'un médiateur central, qui coordonne leurs interactions. Cela permet de réduire les dépendances entre les appareils et de faciliter l'ajout de nouveaux composants au système.


Le médiateur (interface) et le composant (classe abstraite)

// Interface du médiateur : les composants l'utilisent pour signaler un événement
public interface IMediateurDomotique
{
    void Notifier(Appareil expediteur, string evenement);
}

// Composant (classe abstraite) : chaque appareil connaît seulement le médiateur
public abstract class Appareil
{
    public string Nom { get; } // même chose pour Id
    protected IMediateurDomotique _mediateur;

    public Appareil(string id, string nom, IMediateurDomotique mediateur = null)
    {
        // ... (initialisation de id et nom)
        this._mediateur = mediateur;
    }

    protected void NotifierMediateur(string evenement)
    {
        _mediateur.Notifier(this, evenement);
    }

    public void SetMediateur(IMediateurDomotique mediateur)
    {
        this._mediateur = mediateur;
    }
}

Les composants concrets

// Le détecteur ignore l'existence de l'ampoule et de la caméra. Il notifie seulement le médiateur
internal class DetecteurMouvement : Appareil
{
    public void DetecterMouvement()
    {
        Console.WriteLine($"[{Nom}] détecte du mouvement.");
        NotifierMediateur("MouvEstDetecte");
    }

    public void DetecterPlusMouvement()
    {
        Console.WriteLine($"[{Nom}] ne détecte plus de mouvement.");
        NotifierMediateur("MouvEstPlusDetecte");
    }
}

// L'ampoule et la caméra exécutent simplement les actions demandées par le médiateur
internal class AmpouleIntelligente : Appareil
{
    // méthodes qui affichent du texte. Voir le git pour code complet.
    public void Allumer() { /* ... */}
    public void Eteindre() { /* ... */}
}

internal class CameraSecurite : Appareil
{
    public void DemarrerEnregistrement() { /*...*/ }
    public void ArreterEnregistrement() { /*...*/ }
}

Le médiateur concret

// Le médiateur concret : contient toutes les règles d'interaction entre les appareils
internal class MaisonIntelligente : IMediateurDomotique
{
    private AmpouleIntelligente _ampoule;
    private DetecteurMouvement _detecteurMouvement;
    private CameraSecutire _cameraSecutite;

    // La maison se branche comme médiateur de chaque appareil
    public MaisonIntelligente(AmpouleIntelligente ampoule, DetecteurMouvement detecteurMouvement, CameraSecutite cameraSecurite)
    {
        this._ampoule = ampoule;
        this._ampoule.SetMediateur(this);

        this._detecteurMouvement = detecteurMouvement;
        this._detecteurMouvement.SetMediateur(this);

        this._cameraSecurite = cameraSecurite;
        this._cameraSecurite.SetMediateur(this);
    }

    public void Notifier(Appareil expediteur, string evenement)
    {
        if (evenement == "MouvEstDetecte")
        {
            _ampoule.Allumer();
            _cameraSecurite.DemarrerEnregistrement();
        }
        else if (evenement == "MouvEstPlusDetecte")
        {
            _ampoule.Eteindre();
            _cameraSecurite.ArreterEnregistrement();
        }
    }
}

Utilisation

var ampoule = new AmpouleIntelligente("1", "Lumière salon");
var mouvement = new DetecteurMouvement("2", "Détecteur de mouvement");
var camera = new CameraSecurite("3", "Caméra du salon");
new MaisonIntelligente(ampoule, mouvement, camera);

mouvement.DetecterMouvement();     // Ampoule allumée et caméra en enregistrement
mouvement.DetectePlusMouvement();  // Ampoule éteinte et caméra arrêtée
